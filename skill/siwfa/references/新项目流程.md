# 新项目流程

> 版本 v1.3 ｜ 2026-10-26 ｜ 变更：项目统一建在 `Workspace/Project/` 下

**定义**：标准化项目执行 SOP，从接到需求到交付复盘。

**解决**：每次重新发明轮子，方向偏航，需求不收敛。

**目标**：让每个项目按统一节奏推进，可控、可回退、可交付。

### 3.1 步骤 0：选择框架模式

项目启动前，先让用户选择执行模式。用户不选或答复「无偏好」时，默认阶梯模式，并在开工前说明「按阶梯模式执行」。

| 模式 | 定义 | 适用 |
|------|------|------|
| 简单模式 | 背景 + 直接执行呈现结果 | 明确的小任务 |
| 阶梯模式（默认） | 背景 + 各环节可跳跃 | 中等复杂度 |
| 思考模式 | 背景 + 流程完整执行 | 战略级/模糊项目 |

**阶梯模式的默认动作**：⚡ 环节在开工前一次性问清要跳过哪些；用户未答复具体环节时，全部执行。跳过时在 `理解日志.md` 记一条，写明跳过的环节与决定人。

### 3.2 步骤 0.5：技能策展（前置必执行）

1. 检索本地：全局技能库与本分类技能目录，找相关技能。
2. 对比外部：无匹配或老旧时，到 GitHub 或技能市场找更优替代。
3. 择优汰旧：外部更好则安装替换；多年未更新的标记或删除。
4. 记录结果：在 `背景情况.md` 的「技能策展结果」写已装、已用、未匹配三项。

### 3.3 步骤总览（8 步）

1. 创建项目文件夹：`Workspace/Project/Project-编号-项目名称`，并在 `项目台账.md` 登记。`Workspace/Project/` 是全部项目的唯一存放位置，不得在其它位置另建项目目录。
2. 创建 `背景情况.md`，按第 3.5 节模板收集背景。
3. 框架提问：5–10 个核心问题，分 2–3 组提交，每组最多 4 个问题，全部多选题；未答完不输出方向。
4. 盲点扫描 + 三维思路推演：用 `blindspot-audit` 扫盲点，给 3 种解决方向；无该技能时按第 3.7 节内置清单执行。
5. 制定详细方案：目标、任务分解、步骤、资源、时序、难点、交付周期。
6. 预览与交付：3 个 HTML 预览 → 用户选定 → 输出完整版。
7. 交付后修订：48 小时内免费修订一轮，边界见第 3.6 节。
8. 项目收尾：Token 成本核算 + 更新复利与踩坑 + 台账写交付日期与修订截止；修订窗关闭后归档。

### 3.4 三种模式对照

| 模式 | 背景 | 提问 | 盲点 | 推演 | 方案 | 预览 | 修订 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| 简单 | ✅ | ❌ | ❌ | ❌ | ❌ | ✅ | ✅ |
| 阶梯 | ✅ | ⚡ | ⚡ | ⚡ | ⚡ | ✅ | ✅ |
| 思考 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

> ✅ 必执行  ❌ 跳过  ⚡ 用户决定

### 3.5 背景情况模板

`背景情况.md` 必含以下六项。用户不便填写时，Agent 用框架提问补齐并标注「Agent 代填，待用户确认」。

```markdown
# 背景情况 — Project-NNN-名称

**创建日期**：YYYY-MM-DD
**执行模式**：简单 / 阶梯 / 思考
**状态**：需求收敛中 / 执行中 / 已交付 / 已归档

## 一、用户原始描述
（原话照录，不改写）

## 二、目标与成功标准
（这个项目做成什么样算完成，可验证的写法）

## 三、范围
（做什么、明确不做什么）

## 四、交付物与格式
（文件类型、数量、交付位置）

## 五、约束
（时间、预算、工具、环境限制）

## 六、已确认的决定
| 项 | 决定 | 日期 |
|---|---|---|

## 七、技能策展结果
- 已装可用：
- 已用：
- 未匹配，改用：

## 八、待确认
```

### 3.6 修订窗与「一轮」定义

- 时长：交付时刻起 48 小时，以 `项目台账.md` 的交付日期为准。
- 一轮包含：一次集中修订，累计修改不超过交付物总量的 30%，且不改变已确认的范围与目标。
- 不属于一轮：新增需求、改变范围、重做结构。这类按新项目处理，编号自增。
- 超出边界：修订窗关闭后或超出范围时，先报「阻塞」，由用户决定转新项目还是放弃。

### 3.7 内置盲点清单（无 blindspot-audit 时执行）

逐项自问并写进方案，每项给出「本项目是否命中 + 证据」：

1. **需求盲点**：用户没说出来但直接影响结果的前提是什么？谁使用这份产物？
2. **依赖盲点**：外部工具、账号、网络、权限中，哪一项失败会让整步停摆？本地是否有等效替代？
3. **验收盲点**：交付后用什么检查能判定「已完成」？失败长什么样？
4. **成本盲点**：哪些环节会产生超出预期的 token、时间或金钱开销？
5. **可逆盲点**：哪一步做错后难以回退？回退需要什么前置条件？
6. **外部变化盲点**：法规、平台规则、价格、依赖版本近期是否变化？无来源时标「未确认」。

输出格式：命中项 ≤ 7 条，每条写「后果 → 证据 → 最便宜的确认方式」。另写两节：「已覆盖良好」「可暂缓，附复查条件」。

### 3.8 规则

- 所有文件必须且只能放在 `Workspace/Project/<项目文件夹>/` 内。
- 编号从 `Project-001` 开始自增，先查 `项目台账.md` 再分配。
- 涉及代码/工程实现时，进入执行前先读 `工程的原则.md`。
- 状态词只用：已完成 / 部分完成 / 未开始 / 进行中 / 已验证 / 未验证 / 失败 / 跳过 / 阻塞 / 未确认。
